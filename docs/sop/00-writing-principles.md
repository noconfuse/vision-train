# SOP 写作准则

> 本文档是 `docs/sop/*.md` 的唯一写作约束。所有 SOP 在新建 / 修订时必须遵守，并在提交前通过本文"自检表"逐条对照。

## 1. SOP 的定位

SOP 回答两个问题：

- **做什么**：让读者清楚要完成什么业务动作。
- **为什么 / 数据落点**：让读者理解每一步的语义、数据写入位置、参数含义。

SOP 不教用户怎么点屏幕。UI 措辞只能用于"关键约束"和"必要功能存在提示"，详见 §5。

## 2. 硬约束（违反必须改稿）

下列任何一条被违反，视为不合格稿，必须改稿后才能合并：

1. **不允许出现 UI 位置描述**。禁止出现"按钮位于右上 / 工具栏 / 顶部 Tabs / 侧边栏 / 二级菜单 / 进入选择模式 / 卡片右上角 ⋯"等措辞。
2. **不允许写逐步点击路径**。禁止出现"步骤 1 → 步骤 2 → 步骤 3"型的纯交互引导。
3. **不允许写视觉风格**。禁止出现"圆角 / 阴影 / 配色 / emoji / 蓝色 / 深色 / ghost 按钮"等措辞。
4. **不允许把功能写成"在某个 Tab / 子页面 / 浮层中"**。只能写"系统提供 X 功能，入口语义为 Y"。
5. **不允许把 Tab 名 / 菜单名当主语**。应当用业务对象（项目 / 数据集 / 工作流 / 任务）当主语。
6. **不允许在 SOP 里出现"按钮"作为功能名**。按钮不是业务能力，必须用"操作 / 能力 / 任务"代替。
7. **不允许写前端代码位置 / 组件名 / props / 字段**。SOP 描述业务语义，不绑定实现。

## 3. 怎么写一个业务动作

按下面四个要素写，每一项都必须出现：

| 要素 | 必须出现 | 表达模板 |
| --- | --- | --- |
| 业务动作 | 是 | "执行 X（参见 SOP-x）" |
| 触发条件 | 是 | "在 Y 前提下可执行 X" |
| 数据落点 | 是 | "X 会写入 / 修改 <路径或字段>" |
| 参数语义 | 是 | 用表格说明参数 / 字段含义与默认值 |

示例（错误 → 正确）：

- ❌ "点击工具栏的 🤖 自动标注 按钮"
- ✅ "使用自动标注能力（详见 SOP-4）：在数据集已完成导入且已有可用模型的前提下，对所选 split 生成待复核草稿"

## 4. 推荐的章节结构

每篇 SOP 统一使用以下结构：

1. **目标**：一段话讲清本 SOP 解决什么问题。
2. **前置条件**：依赖的项目、数据集、模型、参数、用户权限。
3. **业务动作**：按业务顺序描述要做什么。
4. **数据落点**：明确每一步写入 / 修改的文件、目录、字段、命名。
5. **参数 / 字段含义**：表格说明参数语义与默认值（与 UI 解耦）。
6. **任务状态与失败排查**：常见状态、错误现象、排查方向。
7. **相关 SOP**：跳转链接。

## 5. 例外条款

只有以下两类信息可以用 UI 措辞，但**只能描述功能存在或关键约束**，不能描述位置：

- **新引入的能力**：可以用一句"系统提供 X 功能"作为提示，例如"系统提供 FastAPI 部署模板下载"。
- **关键约束**：例如"删除数据集前系统会要求二次确认"。

不允许借这两类例外把 UI 操作重新塞回 SOP。

## 6. 写完后必须过的自检表

每篇 SOP 合并前，作者需要逐条勾选：

- [ ] 没有出现"按钮位于 / 在 X Tab / 右上 / 顶部 / 侧边栏"等位置描述
- [ ] 没有出现"步骤 1 → 步骤 2"型点击路径
- [ ] 没有出现"圆角 / 阴影 / 蓝 / 红 / ghost / icon"等视觉措辞
- [ ] 章节结构符合本文 §4
- [ ] 每个业务动作都标注了数据落点
- [ ] 参数 / 字段都进了表格而不是散落正文
- [ ] 跨 SOP 跳转都用了相对路径链接
- [ ] 当本轮新增能力时（任务中心、数据集版本、归档 / 恢复、部署模板、Pose 任务），相关章节已补齐

## 7. 适用范围

- 适用：`docs/sop/*.md`。
- 不适用：`docs/guide/*.md`（设计指南，可保留 UI 措辞）、`docs/deploy/*.md`（部署文档）、`docs/README.md` 与 `docs/_coverpage.md`（营销 / 简介）。
- `docs/guide/backend-refactor-todo.md` 与 `roadmap/*` 都不属于 SOP 范畴，不要混入。
