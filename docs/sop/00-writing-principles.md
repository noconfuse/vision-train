# SOP 写作准则

> 本文档为 `docs/sop/*.md` 的统一写作约束。所有 SOP 在新建 / 修订时必须遵守。

## 1. SOP 写什么

SOP 的目标是回答两个问题：

- **做什么**：让读者知道该完成什么业务动作（导入、标注、训练、导出…）。
- **为什么 / 数据落点**：让读者理解每一步的语义、数据写入位置、参数含义。

## 2. SOP 不写什么

下列内容**不属于** SOP，禁止写入：

- 某个按钮 / Tab / 二级菜单在界面上的**具体位置**（"右上角"、"工具栏"、"顶部 Tabs"、"进入选择模式"按钮等）。
- 某个功能**当前所在哪个 Tab / 子页面 / 浮层**。
- 按钮的视觉风格（圆角、阴影、配色、emoji 等）。
- UI 流程的逐步点击路径（"步骤 1 → 步骤 2 → 步骤 3"型的纯交互引导）。

> 这些都属于**产品交互细节**，随着 UI 迭代会频繁变化。一旦写进 SOP，每次改 UI 都要同步改文档，维护成本巨大。

## 3. 怎么替代"按 X 按钮"

- 用**业务动作**描述功能，而不是位置：
  - ❌ "点击工具栏的 🤖 自动标注 按钮"
  - ✅ "使用自动标注功能（详见 SOP-4）"
- 用**结果 / 产物**替代操作路径：
  - ❌ "在 Datasets Tab → 选中数据集 → 切换二级 Tab 到 📊 数据预览 & 标注"
  - ✅ "打开某个数据集，进入数据预览 / 标注视图"
- 用**入口语义**而非**视觉位置**：
  - ❌ "右上角的 ⋯ 菜单"
  - ✅ "项目操作菜单中的编辑 / 删除项"

## 4. 推荐的章节结构

每篇 SOP 推荐结构：

1. **目标**：一段话讲清本 SOP 解决什么问题。
2. **前提 / 输入**：依赖的项目、数据集、模型、参数。
3. **业务动作**：按业务顺序描述要做什么，**不要写"在 UI 上点哪里"**。
4. **数据落点**：明确每一步写入 / 修改的文件目录、字段、命名。
5. **参数 / 字段含义**：表格说明参数含义与默认值（与产品解耦的语义层）。
6. **失败排查**：常见错误与定位思路（同样只写"现象 + 排查方向"，不写 UI 操作）。
7. **相关 SOP**：跳转链接。

## 5. 例外情况

以下情况可以保留少量 UI 措辞，但只描述**功能存在**，不写**位置**：

- 功能是**新引入**且**用户没有其它发现途径**时，可以用一句"界面提供 X 功能"作为提示。
- 某个交互是**必要的关键约束**（例如"删除不可恢复"必须通过二次确认才能触发），可以写"系统会要求二次确认"。

总之：**SOP 不教用户怎么点屏幕，教用户怎么完成业务**。
